# Product Decision — Commercial Strategy for Nibras
**الحالة:** معتمد  
**تاريخ القرار:** 2026-07-26  
**التنفيذ:** مؤجل؛ لا يدخل في الـSprint الحالي إلا كقيود معمارية لا تتطلب واجهة أو دفعاً.

## قرار المنتج
Nibras هو **منصة إنتاج تربوي احترافية لأستاذ الاجتماعيات في التعليم المتوسط الجزائري**. القيمة التجارية هي الخدمة المستمرة الناتجة من تكامل: المعرفة الرسمية الموثقة، Teacher OS، الذكاء الاصطناعي المقيد بالمصادر، المحتوى والأنشطة، التقويم، العلاج والإثراء، وأدوات التخطيط والتنفيذ.

لا يباع المنتج كملفات ثابتة أو شراء دائم. يكون الوصول باشتراك مدته **موسم دراسي واحد** مع تجديد في الموسم التالي. يختار الأستاذ نطاق المستويات التي يدرسها، ولا يمنح تلقائياً الوصول إلى كل المستويات. توجد تجربة مجانية، ويحدد زمنها وحدودها التجارية لاحقاً.

## تقييم Product + Architecture
**القرار سليم** للأسباب الآتية:
- يحول القيمة من ملفات سهلة النسخ إلى خدمة متجددة وموثقة ومخصصة.
- ينسجم مع تحديث المنهاج، والتحسين المستمر للمحتوى، والذاكرة والتخطيط عبر الموسم.
- يتيح تسعيراً عادلاً نسبياً حسب عدد المستويات المستخدمة.
- لا يعيد المنتج إلى نموذج إدارة مؤسسات؛ الاشتراك يرتبط بالأستاذ ومساحة عمله الخاصة وفق ADR-005.

## القيود المعمارية المعتمدة الآن
هذه ليست ميزات تُنفذ الآن، بل عقود يجب ألا يخالفها أي Sprint لاحق:
1. كل مورد أو بحث أو توليد يجب أن يحمل metadata للسنة والمادة والموسم، حتى يمكن تطبيق entitlement لاحقاً دون ترحيل المحتوى.
2. يجب أن يمر الوصول إلى محتوى المستوى عبر طبقة قرار مركزية (`AccessPolicy`/entitlement boundary) عند تنفيذ الاشتراكات؛ لا تزرع فحوص الوصول داخل واجهات منفردة.
3. لا تفترض APIs أو الواجهة أن المستخدم يملك جميع المستويات. في مرحلة MVP الحالية يبقى النطاق مفتوحاً للاختبار الداخلي فقط، ويضاف enforcement عند مرحلة الوصول التجاري.
4. الاشتراك يرتبط بـworkspace الخاص بالأستاذ وacademic year، لا بجهازه ولا بملف ثابت قابل للتنزيل.
5. انتهاء الاشتراك لا يحذف بيانات الأستاذ أو خططه أو مذكراته. السياسة التجارية المستقبلية تحدد read-only/export/retention بوضوح قبل الإطلاق.
6. التجربة المجانية تكون حالة entitlement زمنية، لا نسخة تطبيق منفصلة ولا fork في قاعدة البيانات.
7. لا يعتمد نموذج الحماية على DRM أو منع النسخ وحده؛ الحماية الأساسية هي قيمة الخدمة المتجددة، المصدر الموثق، التخصيص، والتحديثات. تشارك الموارد لاحقاً وفق سياسات وصول واضحة لا وفق «حماية وهمية» للملفات.
8. كل قرار تسعير أو مدة تجربة أو بوابة دفع يبقى خارج الكود إلى حين اعتماد سياسة تجارية مستقلة.

## أثر القرار على Implementation Blueprint
- لا يغير Sprint 0–2 أو مسار MVP الحالي: الوثيقة → المعرفة → مورد → تقويم/علاج.
- يؤجل Epic الدفع، الفوترة، الكوبونات، الفواتير، والواجهة التجارية؛ لا تدخل MVP الحالي.
- قبل أول Pilot تجاري أو إتاحة محتوى متعدد المستويات للمستخدمين، يضاف work item محدد لتنفيذ: catalog + subscription + entitlement + trial + expiration policy + audit + tests. لا يبدأ هذا العمل قبل قرار تجاري مستقل عن السعر والمدة ووسيلة الدفع.
- يبقى نموذج `subjects` و`grade_levels` الذي أنشئ في Sprint 2 مناسباً مباشرة لهذا القرار.
- يبقى نموذج مساحة العمل الخاصة بالأستاذ من ADR-005 مناسباً؛ لا يعاد إدخال school manager أو multi-institution UI.

## ما لا ينفذ الآن
- الدفع الإلكتروني أو مزود الدفع.
- الأسعار والباقات النهائية.
- شاشة الاشتراك أو الفواتير.
- التجربة المجانية الفعلية وحدود الاستخدام.
- حجب المحتوى أو انتهاء الصلاحية.
- إدارة تراخيص المؤسسات.

## نقطة مراجعة إلزامية لاحقة
قبل تنفيذ أي billing/entitlement، يعتمد Product Owner وثيقة تجارية قصيرة تحدد: الموسم، العملة، الباقات، التجربة، سياسة الإلغاء والاسترداد، الوصول بعد الانتهاء، وسيلة الدفع، ومتطلبات قانونية/ضريبية محلية. بعدها فقط ينشأ ADR تقني للتنفيذ.
